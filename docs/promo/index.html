What this actually tests

Not "can an LLM review code" — that's settled. The question is narrower and more useful: does adding a second, independent agent produce real signal a single well-tuned prompt can't reach, or is it just more API spend for the same ceiling?

Phase 1

Code review

Reviewer + independent arbiter + mutual triage on 20 planted-bug PRs from real Flask source. Catches a critical XSS bug every single-agent configuration misses.

Phase 2

Code generation

Same architecture ported to a writer-loop — writer drafts, reviewer + arbiter critique, writer revises. Under 3-seed variance testing, multi-agent beats solo by 2 tasks across 39 runs — same direction as Phase 1, roughly half the effect size a single-seed pilot suggested.

Discipline

Eval-first, always

Every architectural change re-run against the full corpus before being called a win. The ablation (single-agent baseline) runs alongside every multi-agent configuration, every time — without it, the multi-agent number means nothing.

Architecture

Three agents for review, a tighter loop for generation. Independence is the design property being tested in both.

1. Reviewer

Adversarial single-pass review of the diff. Tuned to surface issues, not to triage them.

→

2. Arbiter

Independent second-pass review. Sees the reviewer's findings only as anti-redundancy context — surfaces what the reviewer missed, especially correctness-critical and architectural issues.

→

3. Triage

Two voices (reviewer-style, arbiter-style) independently vote KEEP / DROP / UNSURE on the merged list. Both KEEP → blocking. Both DROP → drop. Mixed → advisory.

Input: a PR diff. Output: a two-tier triaged review — blocking findings and advisory findings — the disposition senior reviewers actually use.

Writer

Drafts code from spec only — never sees the tests, never sees failure tracebacks. Only signal: a binary pass count (e.g. "5 / 17 passing").

⇄

Reviewer

Sees the full attempt history. Catches regression and oscillation across iterations.

+

Arbiter

Sees only the latest attempt — independent second pass, anti-anchoring property carried over from Phase 1.

Loop repeats until tests pass or a 3-iteration budget is hit. Writer-alone (binary signal only, no critique) is the ablation arm run alongside every multi-agent run.

The iteration journey

Four architectural iterations, not prompt tweaks. Each one tested a specific hypothesis about how the second agent should relate to the first.

Worked example — the load-bearing catch

pr_009 introduces a regex-based HTML sanitizer labeled as XSS prevention. It looks reasonable on a quick read. Regex-based HTML sanitization is a long-known anti-pattern — and the single-agent reviewer missed it across every configuration and every prompt variant tried.

1
Single-agent reviewer — empty review

Strong on classic vuln shapes (path traversal, SQLi, credential exposure). "This whole approach is wrong" requires recognizing the bug isn't in a line, it's in the strategy — a different kind of reasoning one prompt pass doesn't reach.

2
Independent arbiter — 5 findings, 3 critical

Framed to look for what the first reviewer missed, especially architectural issues. Caught the non-recursive script-tag removal, the quote-style mismatch on event handlers, and the entirely-unhandled vectors (iframe, object, img onerror) — by treating it as "this approach is wrong," not a per-line bug hunt.

3
Mutual triage — all 3 criticals promoted to blocking

Both triage voices independently voted KEEP on all three critical findings. The single-source risk (only one agent flagged it) didn't tank confidence — both voices reached the same conclusion reading the same diff.

"The miss isn't a prompt problem; it's a single-pass-on-one-model ceiling. The independent arbiter, with a different framing focused on gaps and architectural issues, reaches a class of reasoning the reviewer doesn't."

Phase 2 — seed 1's reading (later shown to be one seed, not a stable effect)

Seed 1 — multi-agent win

task_007 — JSON path resolver

writer-alone:  15 → 16 → 16 (stuck)
multi-agent:   timeout → 17/17

Reviewer + arbiter produced 10 specific findings — bracket parser, mutable sentinel default, dot-handling edge cases, swallowed exceptions. The binary pass-count signal told the writer it was wrong; the critique told it where to look.

Seed 1 — multi-agent loss

task_013 — whitespace normalizer (underspec)

writer-alone:  16 → 12 → 17 (recovered)
multi-agent:   11 → 16 → 13 (diverged)

Spec is genuinely ambiguous on newline-adjacent whitespace. The arbiter asserted a confident interpretation; the writer trusted it and over-corrected, breaking previously passing cases. Critic confidence in the face of spec ambiguity pushes the writer the wrong way — in this run.

Both trajectories are from the iter1 single-seed pilot and are accurate reads of that run. They are not stable effects: re-running the same two tasks across 3 seeds (iter2/iter3) showed each converges or fails depending on seed, for both arms. See the 3-seed numbers above and PHASE_2_FINAL.md for the corrected picture.

Where it loses

The eval-first discipline means the negative results are as documented as the wins — including the time the system found a bug in its own ground truth.

Ground rules, preserved from kickoff

1. Eval-first

Iterate against the corpus every change. No prompt tuning without re-running the eval.

2. Run the ablation

Always score the single-agent baseline alongside the multi-agent run. If the arbiter isn't adding signal, the architecture is wrong — not the prompt.

3. Don't expand the corpus to fit the agent

If the agent fails on a bug class, fix the agent — don't make the bugs more obvious. When the agent catches something the rubric mislabeled, document the discovery; don't silently rewrite the corpus.

4. Bailout

If iteration becomes vibes-only — the eval stops discriminating between prompt variants — switch to mutation testing, where the eval is automatic.
